<objective>
Build the payment-recording backend (OPDN-02, success criterion 1): a `payment` table (booked receipt) plus a `payment_allocation` join so one payment can settle several open items and one open item be settled by several payments (Teilzahlungen). Recording runs in ONE transaction that reduces `OpenItem.OpenAmount`, transitions `OpenItemStatus`, reduces the whitelisted `SalesDocument.AmountDue`, flips `DocumentStatus.Paid` when fully settled, and audits. Payments are GoBD booked facts — append-only; corrections are a reversal payment, never an edit/delete.

Purpose: Close the receivable side of the money loop so a user can record incoming money and see the open-item status update correctly.
Output: `payment` + `payment_allocation` tables (RLS + append-only trigger), `PaymentService`, `POST/GET /api/payments` + reverse endpoint, real-Postgres integration proof.

Create `PaymentService` (scoped) with `RecordAsync` mirroring `SalesDocumentEndpoints.FinalizeCoreAsync` (the `mutate → IAuditWriter.RecordAsync → SaveChangesAsync` idiom inside `db.Database.BeginTransactionAsync`):

```
await using var tx = await db.Database.BeginTransactionAsync(ct);
var payment = new Payment { TenantId = tenantId, Amount = req.Amount, ValueDate = req.ValueDate,
                            Method = req.Method, Reference = req.Reference, RecordedAt = now };
db.Add(payment);                                  // db.Add — NEVER nav-collection .Add (the 03-11 bug)
foreach (var alloc in req.Allocations) {
    db.Add(new PaymentAllocation { TenantId = tenantId, PaymentId = payment.Id,
                                   OpenItemId = alloc.OpenItemId, AllocatedAmount = alloc.Amount });
    var op = await db.Set<OpenItem>().FirstAsync(o => o.Id == alloc.OpenItemId, ct);
    op.OpenAmount -= alloc.Amount;                 // decimal(19,4)
    op.Status = op.OpenAmount <= 0m ? OpenItemStatus.Paid : OpenItemStatus.PartiallyPaid;
    var doc = await db.Set<SalesDocument>().FirstAsync(d => d.Id == op.DocumentId, ct);
    doc.AmountDue = op.OpenAmount;                 // WHITELISTED column
    if (op.Status == OpenItemStatus.Paid) doc.Status = DocumentStatus.Paid; // Paid=4
}
await audit.RecordAsync(new PaymentAuditEvent("payment.recorded", payment.Id, null, snapshot), ct);
await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Validate BEFORE persisting (service-level re-check inside the tx, RESEARCH Pitfall 6): each allocation amount > 0, each target OP exists and is Open/PartiallyPaid, and `alloc.Amount <= op.OpenAmount` (reject over-allocation → return a typed failure the endpoint maps to 422). Use `RoundingPolicy` (Platform.Money) for any rounding; never `float`.

`ReverseAsync(Guid paymentId)` — load the original payment + its allocations (RLS), INSERT a NEW reversal payment (`Amount = -original.Amount`, `ReversesPaymentId = original.Id`) + reversing allocations (`AllocatedAmount = -original`), and for each affected OP restore `OpenAmount += original.AllocatedAmount` and recompute `Status` (Open when back to original, PartiallyPaid when partially settled) + reset `SalesDocument.AmountDue`/`Status` accordingly. NEVER UPDATE/DELETE the original payment (the trigger would raise). Audit `payment.reversed`.

Define a nested `PaymentAuditEvent : IAuditEvent` record (mirror `SalesDocumentAuditEvent`) — `Action`, `EntityType="Payment"`, `EntityId`, `Before`, `After` (JSON snapshot). Tenant/actor are stamped by the writer.
