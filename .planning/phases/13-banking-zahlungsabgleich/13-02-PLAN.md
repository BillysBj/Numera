Add `enum MatchTier { High, Review }`.

    `ReconciliationScorer` — a stateless scoped service taking a `NumeraDbContext` (constructor-injected; RLS gives it only this tenant's rows). Method `Task<IReadOnlyList<MatchCandidate>> ScoreAsync(BankTransaction tx, CancellationToken ct)`:
    1. Guard: if `tx.Amount <= 0` (outgoing/debit) return empty — D2 receivable-only: there is no payable to match to. Only incoming transactions score.
    2. Candidate-filter (avoid N×M): query `OpenItem` `WHERE Status in (Open, PartiallyPaid)` and narrow by a cheap predicate set — items whose `OpenAmount == tx.Amount` (exact) OR whose `DocumentNumber` appears in the extracted references from `tx.Purpose`/`tx.EndToEndId`. Extract candidate document numbers from the Verwendungszweck with a regex tolerant of German invoice formats (e.g. `RE`/`R`/`INV` prefixes + digits, and bare digit runs) before hitting the DB, then `WHERE DocumentNumber IN (...) OR OpenAmount == tx.Amount`.
    3. Score each candidate 0..1 by weighted signals (research signal-strength order):
       - Reference (strongest): exact `DocumentNumber` found in Purpose/EndToEndId.
       - Amount: exact `OpenAmount == tx.Amount` (highest); a partial where `tx.Amount < OpenAmount` is allowed but weaker and stays a proposal (never treat as cleared).
       - Counterparty: `tx.CounterpartyIban == BusinessPartner.Iban` (join via `OpenItem.PartnerId`/`SalesDocument.PartnerId`), else a fuzzy `CounterpartyName` vs partner `Name` match (case/whitespace-insensitive contains). Load the partner IBAN/name for candidate PartnerIds in one query.
       - `SuggestedAllocation = Min(tx.Amount, OpenAmount)`.
    4. Tier: exact amount AND exact reference → `High`; everything else → `Review`. Never emit a tier that implies auto-booking — tiers only rank the queue.
    5. Return ordered by Score descending.

    Keep the money math on `decimal`. No booking, no mutation of OpenItem, no Payment creation here.
