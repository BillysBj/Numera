<objective>
Introduce Abschlagsrechnung + Schlussrechnung as first-class document types and make the shared finalize pipeline compute the down-payment offset correctly: full VAT breakdown, gross deduction via a frozen prepayment child table, and an OpenItem on the RESIDUAL amount. This is the deepest finalize change in the phase and lands first so INV-05 and INV-06 build on a settled path.

Purpose: INV-07 + Decision 4 (LOCKED) — new DocumentType enum values (not flags); itemized-gross-deduction → EN 16931 BT-113 so BT-115 payable = BT-112 − BT-113 + BT-114 (BR-CO-16); the OpenItem uses the residual AmountDue (research-flagged double-receivable trap). No double taxation. Because an Abschlags-/Schlussrechnung IS a finalized, numbered, receivable-creating §14 invoice, it must also be Storno-able and Gutschrift-able — so all FOUR DocumentType.Rechnung gates in the endpoints (pre-finalize dry-run, open-item creation, storno eligibility, credit-note eligibility) are widened, not just the finalize-path two.

ACCEPTED V1 LIMITATION (recorded here + in a must_have note, mirroring how CONTEXT.md documents exclusions): the app does NOT specially validate or undo the down-payment deduction chain. If an Abschlagsrechnung that was already deducted on a finalized Schlussrechnung is later cancelled, there is NO automatic re-computation of that Schlussrechnung's BT-113 / residual AmountDue — the user must correct in the right order (Storno the Schlussrechnung first, then its Abschläge). This is a deliberate v1 boundary, not a bug.
Output: Two new DocumentTypes with their own numbering series, a frozen sales_document_prepayment table (RLS), a FinalizeCoreAsync that produces the correct residual receivable for a Schlussrechnung while keeping the VAT breakdown full, and Storno/Gutschrift eligibility extended to the two new types.
</objective>
