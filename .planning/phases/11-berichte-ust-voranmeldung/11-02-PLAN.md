Create `UstVaCalculator` constructed over `NumeraDbContext` + `RecognitionReader` (tests instantiate directly; DI in Plan 06). Method: `Task&lt;UstVaReport&gt; ComputeAsync(int jahr, string zeitraum, CancellationToken ct)` where `zeitraum` is an ELSTER period code (months `01`-`12`; quarters `41`-`44`). Map the code → date range (quarter 41 = Jan-Mar, etc.).

Logic:
1. Read `LedgerSettings.Besteuerungsart` and the tenant `CompanyProfile.IsKleinunternehmer` (RLS-scoped reads).
2. **Kleinunternehmer gate:** if `IsKleinunternehmer`, return an empty `UstVaReport` with `IsKleinunternehmer = true` and no VAT lines (D3 / research: §19 files no USt-VA). Do NOT emit zero Kz.
3. Choose the recognition source: `Besteuerungsart.Soll` → `ReadSollAsync(from,to)`; `Besteuerungsart.Ist` → `ReadCashRecognitionAsync(from,to)`.
4. **Base Kz (81/86/41) via SIGNED natural-direction netting — this is load-bearing for correctness.**
   - A Stornobuchung posts its reversal on its OWN `EntryDate` (`storno.DocumentDate`) as a **Debit** on the same revenue account (via `ReversalPostingSource`); it does NOT post a negative back into the original invoice's period. So a Credit-only sum silently drops a Storno that lands in a different Voranmeldungszeitraum and OVERSTATES that period's base.
   - For **Soll**: compute each Kz base as `Σ(natural-side rows) − Σ(opposite-side rows)` per Kennziffer/category/rate, where the revenue natural side = **Credit**. Mirror the existing convention in `LedgerEndpoints.GetAccountStatementAsync` (`CASE WHEN direction = naturalDirection THEN +amount ELSE -amount END`). Because `SollRecognitionRow` already carries `Direction`, net the credit rows minus the debit rows for the Kz's revenue accounts. (Do NOT filter to Credit only.)
   - For **Ist**: `CashRecognitionRow.NetAmount` is already signed (reversal allocations carry a negative pro-rata factor from 11-01), so sum `NetAmount` matching the Kz's category+rate — reversals net out inherently. Add a comment noting the two paths handle reversals differently (Soll = signed posting netting; Ist = signed pro-rata).
   - Truncate to whole euros **only at this display boundary** (never mid-aggregation), using the base's floor-to-euro rule; a net that goes slightly negative after a reversal-heavy period is legitimate — do not clamp silently, but document the behavior.
5. Compute **Kz 83 Zahllast** = `round(Kz81_base_untruncated·0.19 + Kz86_base_untruncated·0.07)` to 2dp via `RoundingPolicy` (consistent with booking). Attach the "Ohne Vorsteuerabzug…" `Hinweis`.
6. Only include a `UstVaLine` for a Kz if it has a real recognized amount source (a Kz with genuinely zero bookings still appears as 0 for the producible set 81/86/41/83 — that is honest because the source EXISTS; the OMITTED Kz never appear at all). Add a clear code comment distinguishing "producible-but-zero" (allowed) from "no data source" (omitted).
7. Set `IsFestgeschrieben` by checking whether the period's month(s) `FiscalPeriod.Status == Locked` (mirror `GetAccountStatementAsync`'s only-locked stance); Plan 06 uses it for the "vorläufig" badge.

Money: `decimal` end-to-end; use `RoundingPolicy` for the Zahllast; base euro-truncation only at output.
