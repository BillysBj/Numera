    1. VERIFY: `EventUtility.ConstructEvent(json, signatureHeader, options.WebhookSecret, throwOnApiVersionMismatch: false)` (Pitfall 3 — pass false). On StripeException -> return 400 (Stripe will not treat a 4xx as success). Read the raw JSON only — never model-bind (Pitfall: exact bytes needed).
    2. DEDUPE: insert `ProcessedStripeEvent { EventId = stripeEvent.Id, EventType = stripeEvent.Type }` and SaveChanges; if the unique index throws (DbUpdateException on event_id), the event was already processed -> return 200 immediately (idempotent). NOTE: dedupe happens BEFORE tenant resolution because processed_stripe_event is tenant-agnostic (14-01) — use a NumeraDbContext with no tenant set, or the owner/Hangfire connection, so the insert is not RLS-blocked; confirm which context reaches the non-RLS table (mirror how 14-01 exposed it) and document it in the SUMMARY.
    3. RESOLVE TENANT: extract tenant id from the event object — `checkout.session.completed`: `session.ClientReferenceId` (fallback subscription/customer metadata); `customer.subscription.*`: `subscription.Metadata["tenant_id"]`; `invoice.paid`/`invoice.payment_failed`: subscription-details/line metadata or the subscription's metadata (re-fetch via IBillingProvider.GetSubscriptionAsync if needed). If no tenant id is resolvable, log + return 200 (ack, nothing to do). Parse to Guid.
    4. `scope.ServiceProvider.GetRequiredService&lt;ICurrentTenant&gt;().SetTenant(tenantId)` BEFORE any tenant-scoped NumeraDbContext work (exactly the CheckBankConsentJob pattern).
    5. LOAD + FLIP: load the Tenant (RLS now admits its own row), then per event type apply SubscriptionPlanMapper: set Plan, SubscriptionStatus, StripeSubscriptionId, StripeCustomerId (from checkout.session.completed), CurrentPeriodEnd. Out-of-order safety (Pitfall 2): prefer deriving state from the delivered object; when the delivered status is ambiguous, re-fetch via IBillingProvider.GetSubscriptionAsync (source of truth). Store CurrentPeriodEnd; ignore an event whose subscription state is older than the stored period end when clearly stale. SaveChanges. Return 200.
    Keep the handler side-effect-scoped and fast; log each transition (old plan -> new plan) at Information.
